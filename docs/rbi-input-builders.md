# Сборка входов RBI — продолжение 10.11.2026

После исправления идентификаторов локальная схема — 72, PassportSchema v4: 71 — защищаемая позиция ППК, 72 — общие позиции участков трубопровода. Они уже применены, следующие изменения RBI ledger начинать с **73+**. Сверка экранов и данных — корневой docs/FRONTEND_PARITY_AUDIT.md.

Чистые DF/CoF/PoF/risk kernels уже есть и проверены числовыми references. Пользовательского сценария сохранённых расчётов пока нет. Не выдавать наличие kernels или этих builders за завершение RBI.

## Реализованные первые шаги

`Rbi/Domain/DamageFactorApplicability` переводит серверную проекцию 32 МД в применимость 20 DF-семейств:

- thin — активные 2.B, не component-only, строго INTERNAL;
- ext/cui/ecl/ccl — extf/cuif/extcl/cuicl строго EXTERNAL;
- SSC/HIC и прочие внутренние SCC, HTHA — INTERNAL;
- BF/LASE/885/sigma/механическая усталость — THROUGH.

Активный выиграет у потенциального в одной группе. Отсутствующий/потенциальный статус остаётся потенциальным, не подтверждённым DF=0. Применимость не означает достаточность численных входов. Архивный элемент исключается отдельно от обычного фланца; `flanged_cap` не является обычным фланцем. Не распознавать это свободным текстом имени.

`Rbi/Domain/MaterialStrengthInputs` собирает S/YS/TS по effective values выбранной марки. Для сосуда выбирается `gost`, для трубопровода `rd`. S(T) — линейная интерполяция внутри диапазона доступных точек. За границами нет экстраполяции/подстановки ближайшего значения. YS/TS = номинальное re/rm × S(T)/S(20), как в `old/index.dc.html` inputsOf `_dfThinVM` (блок после строки 4365). Нет S(20)/номинальных свойств — соответствующие YS/TS неизвестны. Ноль не превращается в готовую прочность. Invalid/nonfinite/bool числовые входы отвергаются.

Дополнительно реализованы `RbiDate` (конвенция исходного DF helper, 17 независимых old-reference дат) и `ThinningMeasurementInputs`: MIN элемента, выбор максимальной из трёх скоростей, явный CrT=0, отрицательная измеренная скорость, фактические даты и неполные/будущие замеры. Противоречивые MIN за одну дату блокируют готовность. Первичное ТО до ввода сохраняется как исходный замер, не объявляется автоматически ошибкой.

Эти builders **пока не подключены к HTTP или сохранению запусков**. Дополнительно реализованы `ThinningModifiers`, frozen-таблицы `resources/rbi/input-tables-v1.json` и общий `ThinningInputBuilder`: источники, missing/invalid, явные допущения, FOM/FIP/FDL и вызов ядра только при готовности входов. Семь полных сценариев сборки сверены с оригинальным `__dfThin`. Итог `.tools/df-input-builder-tests.log`: **27 тестов / 491 assertions**, отдельно после полного прогона приложения 287 / 125846. Дальше подключать их через application builder, не вызывать HTTP-контроллеры из другого модуля.

## Следующий законченный сценарий

Типизированные настройки RBI компонента реализованы в **миграции 69**, применённой локально после `.tools/rline-before-component-rbi.dump`. Таблица `equipment_component_rbi_settings`: nullable E, injection/dead-leg, confidence, notes; владельцы, коэффициент 0 < E ≤ 1, SQL-проверки, сериализация через aggregate, запрет переназначения владельца и отката с данными. Не менять уже применённые 68/69 и frozen-схемы. Общая команда карточки обеспечивает права, версию, атомарность и аудит. Отдельных «сохранённых DF» в этой таблице нет.

Контракт `component_rbi` добавлен к PATCH/детальной карточке и Scramble, типы frontend сгенерированы. Форма находится в «Компоненты» у выбранного владельца; неизвестность/«нет»/сброс различаются, автор и результат не принимаются от клиента. Истории Storybook покрывают пустую/заполненную/заблокированную форму, Save/409/member; Node и браузер проверяют sparse patch, десятичную запятую, ошибочный E и мобильный экран.

**Миграция 70 также применена локально** после `.tools/rline-before-rbi-point-owners.dump`: SQL запрещает FIP/FDL-признаки у сегментов, включая явное false. Существующие неправильно принадлежащие факты не перемещаются молча: миграция остановится до явного разрешения. Форма показывает сегменту признаки корневого компонента только для чтения; E остаётся собственным. CSV разделяет исходные ручные настройки и расчётный результат.

Для бесшовного исполнения, фланца и бобышки расчётный E = 1 независимо от старого ручного E (AGENTS.md); интерфейс показывает фиксированное значение. Во всех остальных случаях отсутствующий E остаётся неизвестным. Legacy default E=1 для демонабора потребует явной маркировки генерации.

Добавлены `ThinningSourceAssembly` и application `EquipmentThinningAssessment`: пакетное чтение фактов/материалов в согласованной транзакции, MIN вместо чужих скоростей, независимые TP/coil, подписи источников и reference-таблиц. Марка — только единственное активное точное совпадение, без сопоставления по регистру/похожему имени. Материал/геометрия берутся по дереву; E/confidence — **только своего физического владельца** (в old `holder=sub||sg||e.c`, строки 4388/4658); FIP/FDL — у корневого компонента (`e.c.fip/fdl`, строка 4399), действуют на его элементы, не на соседние компоненты. Будущие инспекции и замеры не уменьшают DF на более раннюю дату анализа. Проекция использует текущие факты МД/материала и явно помечает эту политику; это не восстановление исторического состояния всех источников.

Этот application assessment **пока не имеет отдельного HTTP/React-сценария расчёта и не сохраняет принятые запуски**. Следующий шаг — ledger/команда запуска и API/интерфейс с готовностью, историей и устареванием. JSON допустим для неизменяемого снимка запуска, не для mutable настроек.

1. Подключить реализованный application source snapshot к команде запуска: согласованные блокировки источников и повторная проверка подписи перед принятием. Материалы/потоки/факты могут измениться независимо от версии ЕО. Не брать измеренные скорости из старого ручного поля паспорта.
2. Использовать готовый builder thin (tAn/tIn, Sном/Sотбр/MIN/CrM/CrT, прочность, Pd/D/alpha/E, N A–D, prior/likelihood, FOM/FIP/FDL) с явными missing/invalid и допущениями. Legacy default E=1 и отсутствующие fip/fdl демонабора необходимо материализовать отдельно с маркировкой происхождения; не превращать их в defaults новой карточки.
3. По тем же владельцам — внешняя коррозия/хлоридные/SCC/охрупчивание. Не смешивать наружную технологическую среду и ОС. Коэффициенты из каталога tenant overrides требуют отдельного versioned snapshot. Unsupported mechanical fatigue остаётся явным missing method.
4. Общий execute-command с версиями и source locks; immutable run ledger (версия метода/таблиц, источник, входы и выходы, дата/автор, статус готовности). JSON допустим для неизменяемого свидетельства запуска; mutable исходные факты и ручные настройки должны иметь собственные модели/валидацию. Клиент не отправляет вычисленные DF или автора как принятый серверный результат.
5. Текущая пригодность сохранённого запуска сверяется с подписью источников; старый результат остаётся в истории и помечается устаревшим. Сосуд/каждый змеевик агрегируются независимо. Не терять неизвестный активный фактор при max/sum и не смешивать его с явно неактивным нулём.
6. API + React/Storybook: исходные данные/обоснованные правки, missing/ready/устарел, пошаговый расчёт и история. После этого PoF/CoF/риск связываются принятыми snapshot IDs, а не временным React-state.
7. Сравнить с raw old saved DF/CoF/PoF/risk, которые сейчас лежат только в evidence. Старую отметку «проверено»/старый sig не принимать автоматически за подтверждение нового engine.

## До наполнения rline

Полный demo v11 сейчас включает 241 ЕО и явные входы МД. Ещё остаются физическая модель/схема трубного пучка `tbData EQ0015`, правки `refOv.armtypes/cf581`, два одинаково названных пустых черновика новых марок и остальные явно открытые границы `docs/RESUME.md`. Не придумывать им предметные имена и не считать сохранённое source evidence рабочими нормализованными фактами. Полный preview/rollback не означает применение набора. Публичное развёртывание требует отдельной команды пользователя.

## Конвенции времени, найденные при переносе

В old различаются конвенции: `_dfCommon.tY` для RBI = год + дни от 01.01 / 365.25; толстинометрия/паспортные скорости используют epoch-days / 365.25. Текущий CorrosionCalculator использует долю фактической длины календарного года. Нельзя без проверки просто передать его rates в DF и объявить точное совпадение с old. Следующий measurement builder должен проверяться отдельно на межгодовых/високосных датах; не менять действующую коррозию вслепую. Первичный ТО до даты ввода может быть допустимым исходным замером, его не следует объявлять ошибкой автоматически.

## Остаток исходных каталогов

`refOv.armtypes` содержит 7 правок shortlist (3 да, 4 пусто → false по оригинальному __armList), без добавленных/удалённых строк. `refOv.cf581[35:2]` меняет отображаемый C37 с 1.408×10⁻⁸ на 1408×10⁻⁸ (×1000), соседняя ячейка меняет единицу. Это нельзя молча принять за новую константу расчётного ядра: в old таблица CF задана внутри render reference, необходимо отдельно проследить численное использование. Сохранить исходное свидетельство и явно показать расхождение. Два maroNewList — пустые «Новая марка», без предметного имени; не создавать коллидирующие рабочие марки автоматически.
