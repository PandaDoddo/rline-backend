# Варианты стека backend

Рабочее предложение от 06.11.2026. Выбор сопоставлен с [картой фич](FEATURES.md), [декомпозицией](DECOMPOSITION.md) и существующим [архитектурным планом](architecture.md). Окончательный состав пакетов и их версии утверждается после проверки совместимости.

## Оценка Laravel для R-Line

Laravel подходит как долговременная основа backend. Значительная часть задач связана с паспортами и справочниками, правами, изменениями состояния, файлами, аудитом, поиском и фоновыми операциями. Эти задачи хорошо сопоставляются с его штатными механизмами. Для расчётного ядра требуется собственная предметная реализация, эталоны и контроль версий.

Рекомендуемая форма приложения — модульный монолит с отдельными процессами HTTP и очередей. Границы модулей следуют предметным областям. Начальные кандидаты — доступ, организации, установки, каталоги, оборудование, потоки, диагностика/измерения, расчёты, документы и обмен.

Это проектная оценка по нашему функционалу. Документация Laravel подтверждает наличие валидации, авторизации, транзакций, очередей и файлового хранилища. [Laravel](https://laravel.com/docs/13.x), [очереди](https://laravel.com/docs/13.x/queues), [файлы](https://laravel.com/docs/13.x/filesystem).

## Предлагаемая базовая сборка

| Часть | Предложение | Применение в R-Line |
| --- | --- | --- |
| Runtime | PHP 8.5 с актуальными исправлениями | Совместимый с Laravel 13 вариант. Точная версия проверяется с выбранными пакетами и окружениями поставки |
| Framework | Laravel 13 | HTTP API, валидация, политики доступа, транзакции, команды и фоновые задания |
| База | Поддерживаемая PostgreSQL, кандидат — 18 | Основные связи и история, измерения, версии расчётных входов, индексы под реестр |
| HTTP-процессы | Nginx и PHP-FPM | Базовая конфигурация поставки и измерения производительности |
| Фоновые операции | Laravel Queue, рабочий кандидат Redis + Horizon | Импорт, экспорт и пакетные расчёты. Состояние предметной операции и результаты фиксируются в PostgreSQL |
| Файлы | Laravel Filesystem/Flysystem и выбранное S3-совместимое хранилище | Содержимое документов и файлов экспорта, отдельное от паспортных полей |
| Проверки | Статический анализ, интеграционные проверки и численные эталоны | Совместимость контрактов, права, повтор команд, конкурентные изменения и перенос JS-ядер |

PostgreSQL поддерживает major-ветку пять лет. Laravel предоставляет абстракцию файлов и драйверы очередей. Horizon требует Redis и документирует ограничение совместимости с Redis Cluster, поэтому его выбор связан с топологией инфраструктуры. [PostgreSQL](https://www.postgresql.org/support/versioning/), [Laravel Filesystem](https://laravel.com/docs/13.x/filesystem), [Laravel Queues](https://laravel.com/docs/13.x/queues), [Horizon](https://laravel.com/docs/13.x/horizon).

| Решение | Что предоставляет | Предлагаемая роль |
| --- | --- | --- |

| Laravel Fortify | Серверные сценарии аутентификации, восстановления и TOTP-2FA | Подключить нужные сценарии к собственным React-формам. SMS и корпоративные провайдеры имеют отдельную интеграцию |

| stancl/tenancy | Инициализация контекста организации, инструменты отдельных БД, миграции и контекст очередей | Основной кандидат при сохранении решения «одна БД на организацию» |
| spatie/laravel-multitenancy | Минимальные механизмы выбора организации и переключения контекста | Альтернативный кандидат при желании явно управлять переключением соединений и своей обвязкой |
| Laravel Horizon | Управление и мониторинг Redis-очередей | Наблюдение за ожиданием/ошибками/воркерами; предметные состояния расчёта задаёт наше приложение |
| spatie/laravel-activitylog | Запись изменений моделей и пользовательских действий | Возможный вспомогательный механизм. Предметные события диагностики и версии расчётов проектируются отдельно |

Sanctum описывает cookie/session-подход для SPA. Fortify предоставляет headless-сценарии, включая TOTP. Spatie публикует совместимость permission с Laravel 13. Ветка stancl/tenancy 3.x также объявляет совместимость с Laravel 13. Конкретные стабильные релизы пакетов должны быть зафиксированы по результатам Composer-проверки. [Sanctum](https://laravel.com/docs/13.x/sanctum), [Fortify](https://laravel.com/docs/13.x/fortify), [Permission](https://spatie.be/docs/laravel-permission/v8/prerequisites), [stancl composer.json](https://github.com/archtechx/tenancy/blob/3.x/composer.json).

stancl содержит инструменты работы с несколькими БД, включая PostgreSQL и отдельные схемы. Spatie описывает свою философию минимального набора механизмов и поддерживает одну/несколько БД. Для выбора нужно проверить одинаковый сценарий организации, очереди и переключения контекста в двух пакетах. [stancl multi-database](https://tenancyforlaravel.com/docs/v3/multi-database-tenancy/), [stancl queues](https://tenancyforlaravel.com/docs/v3/queues/), [Spatie multitenancy](https://spatie.be/index.php/docs/laravel-multitenancy/v4/introduction), [activitylog](https://spatie.be/docs/laravel-activitylog).

### Filament

Filament строит серверный интерфейс на Livewire, Alpine и Tailwind. Он подходит для отдельной служебной панели организаций, пользователей, справочников и поддержки. Это может ускорить административный контур, если согласовано появление второго интерфейса рядом с существующей React-админкой. [Документация Filament](https://filamentphp.com/docs/5.x/introduction/overview).

Пользовательские таблицы УЗТ, выделение диапазонов и карточки R-Line уже реализованы на React. Использование Filament для этих экранов потребует отдельного решения о переносе UI. Для служебной панели важен вызов тех же предметных команд и политик, которые использует API, чтобы правки через панель имели одинаковые проверки и аудит.

### API Platform

API Platform поддерживает Laravel и Symfony, генерирует OpenAPI, пагинацию и стандартные операции ресурсов, допускает собственные providers/processors. У нас это кандидат для справочников и повторяющихся API-ресурсов. [Laravel integration](https://api-platform.com/docs/laravel/), [state processors](https://api-platform.com/docs/core/state-processors/).

Команды проверки этапа, сохранения многовкладочной карточки, применения периодичности и запуска расчёта имеют свои транзакционные правила. Их нужно оформлять явными прикладными операциями, при необходимости через собственные processors. Решение о подключении API Platform целесообразно принять на одном справочнике и одной сложной команде после сравнения с обычными Laravel Form Requests, Resources и handlers.

### Octane и постоянно работающие HTTP-воркеры

Octane поддерживает постоянно загруженное приложение через отдельные application servers. Его преимущество относится к обслуживанию запросов и повторной инициализации приложения. Для CPU-затратного расчёта нужно отдельно измерять время самого алгоритма и число рабочих процессов. [Laravel Octane](https://laravel.com/docs/13.x/octane).

Стартовая точка для сравнения — PHP-FPM. Переход к постоянным воркерам потребует проверки отсутствия сохранённого контекста предыдущей организации, очищаемости кэшей и поведения долгоживущих зависимостей.

## Архитектура расчётного контура

Предлагаемые границы — прикладная команда получает входы из паспортов/измерений, фиксирует снимок и версии, запускает чистое расчётное ядро, сохраняет результат и объяснение. Ядро получает типизированные входы и не читает текущий запрос, текущую организацию или живые ORM-модели.

Каждое семейство DF, CoF, PoF, RISK, ресурс и ППК получает эталоны из текущего JS с учётом принятых предметных исправлений. Финансовые суммы, округление, научные вычисления с float и допустимые отклонения оговариваются по показателю. Снимок должен воспроизводить результат после обновления каталога или паспорта.

Масштаб из прежнего плана — около 50 организаций и до 50 000 ЕО — не определяет нагрузку сам по себе. Для оценки нужны число элементов/CML/дат на ЕО, количество прогнозных точек и одновременно запускаемых расчётов. Измерение одного большого RISK и пакетного запуска задаст число расчётных воркеров и границы синхронного API.

## Уточнения к прежнему плану

1. Для старта обновить Laravel 11 до поддерживаемой major-ветки по согласованному решению.
2. Долговременную архитектуру выбирать с возможностью развивать выбранный фреймворк. В старом плане переход Laravel → Symfony фигурировал как возможный рост; основание такой миграции потребуется подтверждать отдельно.
3. Отдельные БД в общем PostgreSQL-кластере задают разделение данных и отдельные соединения. Выделенные ресурсы и отдельный контур поставки описываются отдельными инфраструктурными решениями.
4. Tenant-пакет требует настройки контекста для HTTP, очередей, файлов, кэша и миграций. Границы изоляции проверяются собственными интеграционными сценариями.
5. Заявленные требования доступности требуют отдельного инфраструктурного проектирования. Выбор фреймворка сам по себе не подтверждает достижение SLA.
