## Первый сквозной сценарий

Инженер входит в организацию → выбирает установку → создаёт ЕО по типу и профилю → заполняет паспорт → сохраняет → открывает реестр → видит сохранённые значения → повторно открывает карточку.

Сценарий проверяется на новой пустой ЕО и на импортированном объекте с ранее сохранёнными данными.

### B0. Правила данных и контракт первого сценария

Фичи F03, F07, F08, F23.

- [ ] Сопоставить поля создания ЕО, паспорта и колонок реестра. Для каждого поля указать тип, единицу, допустимую пустоту, справочник и источник значения.
- [ ] Разделить внутренний ID, техпозицию, регистрационный и заводской номера. Зафиксировать область уникальности после предметного решения.
- [ ] Описать профиль карточки по типу оборудования и применимому НТД, доступные поля и ограничения правки.
- [ ] Определить команды создания/обновления и ответы чтения для карточки, списка и справочников. Зафиксировать формат ошибок полей, отсутствия данных, запрета доступа и конфликта версии.
- [ ] Определить передачу дат, единиц, десятичных значений и происхождения приближённой даты. Отдельно сохранить признак «уточнить» для даты, известной только по году.

Готово, когда каждое поле первого сценария имеет согласованный источник и frontend может однозначно показать сохранённое, пустое и ошибочное значение.

### B1. Пользователь, организация и доступ

Фичи F01, минимальная часть F02.

- [ ] Реализовать вход, текущего пользователя и выход с серверным сеансом в рамках выбранной архитектуры.
- [ ] Зафиксировать разрешения чтения и изменения ЕО и паспортов для ролей первого сценария.
- [ ] Связать операции с контекстом организации. Проверять доступ к самой ЕО и всем передаваемым ссылкам на установку и справочники.
- [ ] Разобрать реальные сценарии второго фактора, повторной отправки и завершения сеанса. Демо-код выделить в данные демонстрационного окружения.
- [ ] Проверить отсутствие доступа к объекту другой организации через список, прямой ID и операцию изменения.

Готово, когда сервер устанавливает пользователя и организацию для каждой операции, а запрещённое действие отклоняется до изменения данных.

### B2. Размещение и справочники для создания ЕО

Фичи F03 и часть F07.

- [ ] Описать минимальное дерево размещения, связь установки с производством и организацией.
- [ ] Реализовать получение доступного дерева и списка установок с поиском.
- [ ] Подготовить типы оборудования, профили карточек, НТД и места регистрации для первого сценария.
- [ ] Зафиксировать применимость профиля к типу и НТД. Обработать удалённую или недоступную ссылку.
- [ ] Подготовить контролируемую загрузку начальных справочников с версией набора.

Готово, когда можно выбрать существующую установку и применимый профиль без браузерных генераторов данных.

### B3. Создание ЕО и хранение паспорта

Фича F08. Зависит от B0–B2.

- [ ] Описать ЕО, идентификационные атрибуты, принадлежность установке и структурированные поля паспорта.
- [ ] Реализовать создание с введёнными полями. Остальные значения остаются пустыми до заполнения или разрешённого авторасчёта.
- [ ] Реализовать получение полной карточки и обновление разрешённого набора полей.
- [ ] Проверять справочные ссылки, типы, единицы, допустимые диапазоны и сочетания, определённые профилем. Условия оформить в правилах B0.
- [ ] Определить атомарную границу сохранения, учитывая, что текущий frontend объединяет правку паспорта с несколькими вкладками. В первом блоке сохранять согласованный набор паспортных полей одной операцией.
- [ ] Добавить версию объекта и обнаружение конкурирующей правки. Повтор отправленной команды после сбоя должен иметь определённое поведение.
- [ ] Учесть отметки проверки атрибутов и правила их изменения после правки значения.

Готово, когда созданная и изменённая карточка воспроизводится после повторного входа, а частичный сбой сохранения оставляет согласованное состояние.

### B4. Реестр как представление паспорта

Фича F23. Зависит от B3.

- [ ] Определить выборку колонок первого блока и их отображение из паспортных данных.
- [ ] Реализовать фильтрацию по размещению и атрибутам, поиск, сортировку и ограниченную выдачу строк.
- [ ] Добавить устойчивый порядок с внутренним ID для строк с одинаковым значением сортировки.
- [ ] Определить семантику общего количества, фильтрованного количества и выбора всех результатов.
- [ ] Согласовать получение диапазона для копирования, включая строки за пределами загруженного окна. Копирование должно использовать порядок и фильтр того же набора.
- [ ] Возвращать пустые значения в согласованном формате. Значения ресурса и риска до появления расчётных модулей должны иметь явное состояние отсутствия результата.
- [ ] Подобрать индексы под фактические запросы и согласовать измеримые ограничения по объёму выдачи и времени ответа на тестовом наборе.

Готово, когда карточка и реестр показывают один источник значений, фильтры не меняют доступность чужих данных, а загрузка следующей страницы не теряет и не дублирует строки в рамках согласованной семантики чтения.

### B5. История изменений

Фича F25. Включается в B1–B4.

- [ ] Записывать создание и изменение ЕО с пользователем, организацией, серверным временем и версией объекта.
- [ ] Сохранять изменённые поля и прежние/новые значения по согласованной политике.
- [ ] Обеспечить согласованность сохранения паспорта и записи события аудита.
- [ ] Реализовать получение истории объекта с ограничением доступа и постраничной выдачей.
- [ ] Различить событие эксплуатации, выполненную диагностику и техническую запись об изменении поля.

Готово, когда каждое успешное изменение паспорта объясняется записью с автором и содержимым, а отклонённая правка не выглядит как успешное изменение.

### B6. Перенос демонстрационного набора

Фича F26 в объёме первого блока.

- [ ] Инвентаризировать `rldata.js`, `cardOv`, `newUnits`, `inst`, `instNew` и профильные справочники. Определить, какие исходные значения уже прошли миграцию «карточка — первоисточник».
- [ ] Сопоставить старые ID с новыми идентификаторами без потери ссылок. Старые ID сохранить для импорта зависимых компонентов, диагностик и CML.
- [ ] Подготовить отчёт до записи с отсутствующими ссылками, неподдерживаемыми профилями и неоднозначными полями.
- [ ] Обеспечить повторный запуск импорта без появления дублей и перезаписи пользовательских изменений без согласованного режима.
- [ ] Сопоставить количество ЕО и значения выбранных паспортов до и после переноса.

Готово, когда тестовый набор переносится воспроизводимо, а новая ЕО после импорта сохраняет правила пустого паспорта.

### B7. Подключение frontend

Фичи F01, F03, F07, F08 и F23.

- [ ] Выделить обращения к данным для первого сценария и подключить их к согласованному контракту.
- [ ] Сохранить режим черновика и отмену правки. Отменённая правка не отправляет команду сохранения.
- [ ] Показывать ошибки валидации, запрет доступа, потерю сеанса, недоступность сервера и конфликт версии с сохранением введённого черновика.
- [ ] Согласовать, какие настройки представления остаются локальными, а какие привязаны к пользователю на сервере.
- [ ] Сохранить сценарии Storybook с контролируемыми данными и отдельный демонстрационный режим.

Готово, когда вход, выбор установки, создание ЕО, правка паспорта и реестр работают через backend по обычным точкам входа интерфейса.

### B8. Приёмка первого блока

- [ ] Создать ЕО с минимальными данными. Проверить пустые необязательные поля в карточке и реестре.
- [ ] Сохранить паспорт и повторно открыть его в другом сеансе. Сопоставить значения с реестром.
- [ ] Проверить доступ двух организаций и роли без полномочий на запись.
- [ ] Одновременно изменить одну ЕО двумя пользователями. Проверить предусмотренный конфликт и сохранность обеих пользовательских попыток.
- [ ] Повторить создание/сохранение после имитации сетевого сбоя. Проверить согласованное поведение повторной команды.
- [ ] Прочитать несколько страниц реестра с фильтром и одинаковыми значениями сортировки. Проверить количество, порядок и диапазон копирования.
- [ ] Повторно импортировать тестовый набор. Проверить отсутствие дублей и согласованную обработку конфликтов.
- [ ] Проверить историю каждого сохранённого изменения.
