## Политика полноты

Активные механизмы передаются явно. Отсутствующий DF активного механизма даёт неполный результат и список missing; нулевой вклад разрешён для явно неактивного механизма либо сохранённого вычисленного нуля. Отсутствующие gff, тип коррозии или оценка управления блокируют соответствующий итог. Старое неявное pscore=72 не применяется к реальным установкам. Если это значение входит в эталонный набор, оно должно быть отдельным явным входом с происхождением.

ГИ/ПИ не засчитывается в составе ЭПБ. Рекомендации риска не становятся фактом инспекции или принятым планом автоматически. Сосуд и каждый змеевик сохраняют независимые расчётные области. Неполный расчёт парка не получает зелёную категорию по умолчанию.

## Численная устойчивость и известные различия

В DF утонения апостериорные вероятности вычисляются через log-sum-exp. Для обычных входов это та же формула Байеса и совпадение с эталоном. При очень большом числе инспекций старый код обнулял все произведения и подставлял 1/3 для каждого состояния; новая версия сохраняет вычисленный результат. Случай 10 000 инспекций проверен отдельно. Невозможная таблица вероятностей возвращает ошибку, не равномерное предположение.

Неполная тройка измеренной скорости/толщины/даты не переключает расчёт незаметно на проектную скорость. Неиспользуемая ветвь SRP без исходных данных остаётся пустой. Версия PoF сохраняет числовую константу e из прежнего ядра для воспроизведения существующих результатов.

## Анкета управления и различие формул old

Таблицы rbi_management_sections/questions/options — версия определения анкеты. Ответы installation_management_answers типизированы: состояние, bool либо числовая оценка, комментарий; множественный выбор — отдельные installation_management_selections с FK на ответ и допустимый пункт. Сохранение PATCH /installations/{id}/management использует общую версию и блокировку установки, права owner/admin, событие аудита и атомарную транзакцию. Незавершённая анкета показывает прогресс, но score/Fms для PoF остаются null. Неприменимость даёт полный балл только с явным обоснованием; комментарий доступен у каждого вопроса.

В old/mscheck.js Fms=10^(1−0,02·P), а в old/pofcalc.js Fms=2,38·e^(−0,012·P). Обе величины воспроизводятся под разными именами; потребитель PoF использует pof-old-v1, без незаметной подстановки значения из чек-листа. Это расхождение исходника, а не эффект нормализации.

В CoF формула 3.62 сохраняет фиксированный курс 100 RUB/USD как явную политику версии. Остальные расходы передаются в указанных единицах; неизвестные расходы/давление/плотность/доли не заменяются нулём. Явный нулевой множитель сохраняется, в отличие от старого `value || 1`. Будущий сценарий риска не создаёт фактическую инспекцию; отключённая цель null не сравнивается с нулём. Механическая усталость остаётся неподдержанной с явной причиной, вместо старой заглушки DF=0.

## Следующие обязательные части

- Предметные входы DF: материал/температурные характеристики, компоненты/пространства/потоки, инспекции и параметры механизмов.
- Предметные сборщики входов CoF/DF и применение проверенных ядер через сохраняемые расчётные запуски; механическая усталость требует полноценной методики.
- Типизированные gff/цели/матрица, анкета управления и каталог коэффициентов с версиями.
- Неизменяемые запуски, явные связи зависимостей, проверка актуальности и история; JSON допустим как документ снимка, предметные связи хранятся FK.
- API/React/Storybook и полная приёмка; затем идемпотентное заполнение локального rline данными old с отчётом.
