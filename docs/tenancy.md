# Тенанты и отдельная авторизация

Реализовано 06.11.2026. Основные таблицы учётных записей находятся в общей PostgreSQL-БД `rline`. Данные каждого тенанта получают отдельную БД и отдельную PostgreSQL-роль. Подключение и переключение выполняются через Laravel `TenantContext`; stancl/tenancy в текущую реализацию не установлен.

## Что работает

- Стартовый тенант `rline`, перенос существующих пользователей в него. Локальная учётная запись `inspector@rline.local` назначена администратором платформы и владельцем `rline`; её пароль остался прежним в `backend/.tools/local-account.txt`.
- Создание, чтение, переименование, приостановка и возобновление тенантов. Удаление тенанта и его данных через API не предоставлено.
- Отдельный набор провайдеров каждого тенанта: Local, LDAP, AD, Multifactor. Разрешается несколько провайдеров одновременно; способ входа конкретного пользователя определяется его членством в этом тенанте.
- Один глобальный пользователь может быть владельцем одного тенанта, участником другого и входить в них разными способами. Глобальный локальный пароль и TOTP относятся к учётной записи; LDAP/AD/OIDC subject — к членству.
- Вход, MFA, OIDC, восстановление пароля и сеансы привязаны к тенанту. Подмена `X-Tenant` не переключает авторизованный сеанс. Требуется явный выбор организации и повторный вход.
- Зашифрованные `auth_config` и `database_config`, скрытые в JSON. API настроек возвращает признаки наличия секретов, но не их значения.
- Фоновая подготовка PostgreSQL-БД через очередь и сервис Compose `worker`. Имя БД и роли генерируется по числовому ID: `rline_t_<id>`. Ошибка не удаляет данные; повтор `tenant:provision` продолжает подготовку.
- Контекст запросов очищается после ответа. `TenantJobContext` устанавливает и очищает контекст предметной фоновой задачи, включая случай исключения. `TenantModel` использует соединение `tenant`; при отсутствии контекста соединение не настроено.
- Демонстрационные рабочие данные React разделены по `tenant:<id>:` в localStorage и по базе резервных копий IndexedDB. Исходное неразделённое рабочее пространство однократно копируется только в `rline`, исходник сохраняется.

Предметные таблицы оборудования/диагностик ещё не перенесены в backend: новая БД содержит служебную `tenant_identity`. Это разделение инфраструктуры и авторизации; реестр frontend пока работает на прежних демонстрационных данных, с отдельными локальными правками для каждого тенанта. Полная матрица прав F02, приглашения и управление сотрудниками остаются следующими задачами.

## Работа в интерфейсе

Откройте frontend, укажите **код организации** и нажмите **«Выбрать организацию»**. Стартовый код — `rline`. После выбора показываются только включённые способы входа этой организации. Для Local/LDAP/AD после первого входа потребуется своё приложение TOTP, если оно ещё не настроено.

Администратор платформы: **Аккаунт → Панель администратора → Управление тенантами**. Здесь доступны создание, название/статус и провайдеры. БД нового тенанта создаётся worker автоматически; кнопка «Обновить состояния» показывает результат подготовки. Создатель получает членство владельца с Local. При использовании только корпоративного входа сначала предоставьте владельца/администратора с соответствующим provider/subject, затем отключайте Local.

Владелец/администратор организации: **Аккаунт → Настройки профиля → Организация**. Доступны только настройки своего тенанта. Обычный участник их не получает. Сервер проверяет полномочия независимо от видимости кнопок.

Пароль Bind и Client Secret не читаются из API. Пустое поле сохраняет прежний секрет. Сохранение настроек провайдеров меняет `auth_version`: старые сеансы и незавершённые подтверждения потребуют нового входа. Интерфейс завершает текущий сеанс при изменении собственного тенанта. Нельзя отключить все способы входа или оставить тенанта без активного владельца/администратора с включённым провайдером.

Для приостановленного тенанта вход и запросы недоступны. При смене статуса также меняется версия авторизации, поэтому возобновление не возвращает прежние сеансы. Приостановить текущий тенант через его собственный сеанс нельзя.

Одна session cookie относится к одной организации. Вкладка с прежним кодом при смене сеанса в другой вкладке получает отказ; параллельный вход в разные организации возможен в разных профилях браузера. Код тенанта не является секретом, но публичного API перечисления всех организаций нет.

## Запуск Docker

Из `backend`:

```sh
docker compose build app worker
docker compose run --rm app composer install --no-interaction
docker compose run --rm app php artisan migrate --force
docker compose up -d --wait
```

`worker` читает очередь общей БД и должен иметь права создания БД и ролей в PostgreSQL. Локальный контейнер ими располагает. После изменения кода worker используйте `php artisan queue:restart` в контейнере или пересоздайте сервис. При изменении Dockerfile пересоберите образы. Nginx использует DNS Docker для обновления адреса пересозданного PHP-контейнера.

Рабочие настройки сеансов и кэша:

```dotenv
SESSION_DRIVER=tenant-database
SESSION_LIFETIME=30
CACHE_STORE=database
QUEUE_CONNECTION=database
```

`tenant-database` сохраняет `tenant_id` в таблице sessions. Тесты используют отдельный PostgreSQL-контейнер и свой драйвер сеансов `array`.

## Административные команды

```sh
# Предоставить полномочия платформы существующей глобальной учётной записи
docker compose exec app php artisan tenant:platform-admin admin@example.org

# Создать тенант и сразу подготовить его БД
docker compose exec app php artisan tenant:create customer-a "Заказчик А" --owner=admin@example.org

# Создать новую глобальную учётную запись и членство
docker compose exec app php artisan auth:user-create engineer@example.org --tenant=customer-a --name="Инженер"

# Добавить уже существующего пользователя или изменить его привязку входа
docker compose exec app php artisan tenant:user-add customer-a engineer@example.org --role=member --provider=ldap --subject="<entryUUID>"
docker compose exec app php artisan tenant:user-add customer-a ad-user@example.org --role=admin --provider=ad --subject="<objectGUID-lowercase-hex>"
docker compose exec app php artisan tenant:user-add customer-a oidc-user@example.org --role=owner --provider=multifactor --subject="<sub>"

# Повторить подготовку БД после устранения ошибки
docker compose exec app php artisan tenant:provision customer-a
```

Команда членства требует уже существующего глобального пользователя. Для нового внешнего пользователя сначала выполните `auth:user-create` с `--tenant`, `--provider`, `--subject`; e-mail должен быть глобально уникален. Повторное предоставление членства отзывает его прежние сеансы в этом тенанте. Само совпадение e-mail из внешней системы не создаёт связи с глобальным пользователем.

## Настройки провайдеров

После этой миграции `.env` больше не служит изменяемой конфигурацией авторизации всех организаций. Значения из него были однократно перенесены в `rline`; новые тенанты начинают только с Local. LDAP/AD bind-секреты и OIDC credentials не наследуются от другого тенанта или из глобального окружения.

Для настройки используйте UI либо JSON-файл, например `backend/.tools/customer-a-auth.json` (не отправлять секреты в Git):

```json
{
  "local": { "enabled": true },
  "ldap": {
    "enabled": true,
    "uri": "ldaps://ldap.customer-a.example:636",
    "base_dn": "ou=people,dc=customer-a,dc=example",
    "bind_dn": "cn=rline-reader,ou=services,dc=customer-a,dc=example",
    "bind_password": "<secret>",
    "start_tls": false
  }
}
```

```sh
docker compose exec app php artisan tenant:auth-config customer-a .tools/customer-a-auth.json
```

Обновление частичное: отсутствующие провайдеры и поля сохраняются. Для явного удаления секрета передайте `null` при выключенном провайдере. Для LDAP/AD обязательно LDAPS либо StartTLS с проверкой сертификата. Установите корневой сертификат внутреннего УЦ в доверенные сертификаты PHP-образа. Для AD используются такие же поля, ключ `ad` и логин sAMAccountName; для LDAP — uid.

Multifactor:

```json
{
  "multifactor": {
    "enabled": true,
    "issuer": "<exact issuer>",
    "discovery_url": "https://api.multifactor.ru/.well-known/openid-configuration",
    "client_id": "<tenant client id>",
    "client_secret": "<tenant client secret>"
  }
}
```

Callback приложения остаётся `MULTIFACTOR_CALLBACK` из `.env` (один адрес приложения); контекст тенанта сохранён в защищённом сеансе и связан с OIDC state. У каждого тенанта свои issuer/client credentials. Первый и второй факторы настраиваются на соответствующем ресурсе Multifactor. Требования TLS, RS256, PKCE и nonce описаны в [authentication.md](authentication.md). Живые LDAP/AD/Multifactor требуют реальных серверов и ключей для интеграционной приёмки; локальные тесты используют подмену транспорта.

## Контракт

| Метод и путь | Доступ |
| --- | --- |
| POST `/auth/tenant`, тело `{tenant: "slug"}` | Явный выбор активного тенанта, сброс предыдущего сеанса и pending MFA |
| GET `/auth/providers` | Только безопасная информация о провайдерах выбранного тенанта |
| GET `/auth/me` | Пользователь, признак platform admin, текущий tenant и роль членства |
| GET/POST `/api/tenants` | Только администратор платформы; список с пагинацией/создание |
| PATCH `/api/tenants/{id}` | Только администратор платформы; name/status |
| GET/PUT `/api/tenants/{id}/authentication` | Платформа либо owner/admin текущего тенанта; маскированные настройки |
| GET `/api/tenant/database` | Авторизованный пользователь с MFA; проверка БД текущего тенанта |

React передаёт `X-Tenant`. Параметр `tenant` в URL используется для redirect/reset links; противоречащие заголовок и параметр отклоняются. Если оба отсутствуют, используется привязанный tenant сеанса, затем стартовый `rline`. Вход, session restore и password broker работают только после определения контекста. Reset-токены имеют составной ключ tenant/e-mail. Изменение внешней identity или пароля делает прежнее MFA-подтверждение недействительным.

Полномочия платформы не выдаются через профиль или членство. Session API показывает и отзывает только свои сеансы текущего тенанта. Изменение глобального локального пароля отзывает другие сеансы учётной записи независимо от тенанта. Аудит хранит tenant актора и target_tenant_id для административных действий.

## Проверки

```sh
docker compose --profile test up --build --abort-on-container-exit --exit-code-from test test
docker compose --profile test stop db-test
docker compose exec app composer validate --strict
docker compose exec app composer lint
```

Во frontend: `npm run build`, `npm run lint`, `npm run build-storybook`, `node tests/tenant-storage.mjs` (Node с поддержкой импорта TypeScript). Storybook: `R-Line/Тенанты`, состояния владельца и администратора платформы.

Проверены реальное создание двух изолированных БД и отказ подключения чужой роли, разные провайдеры одного пользователя, отказы межтенантных запросов и reset-токенов, версии сеансов, шифрование/маскирование секретов. В браузере проверены создание через админку, очередь, изменение провайдеров, повторный вход в другой тенант и разделение localStorage. Временный проверочный тенант и его пустая БД удалены.

Результат 06.11.2026: 45 серверных тестов / 144 проверки; frontend, Storybook, Composer validate, Pint и проверка tenant-storage прошли.
