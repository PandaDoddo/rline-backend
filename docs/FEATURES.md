# Карта фич frontend

Дата среза 06.11.2026. Основание — код frontend на `7559faf`.

## Как читать карту

ЕО — единица оборудования. CML — место контроля толщины. МД — механизм деградации. ФТС — сводка фактического технического состояния.

«Локальная логика» означает работу с состоянием браузера. «Расчёт» означает наличие исполняемого расчётного кода. «Демо» означает имитацию или генерацию данных. У одной фичи могут сочетаться несколько состояний.

## Зависимости предметных фич

1. F01–F02 задают пользователя, организацию и доступ для остальных операций.
2. F03 и F07 задают размещение, типы и профиль паспорта F08.
3. F08 → F09 → F13 → F14 образуют цепочку состава, измерений и ресурса. F12 задаёт диагностические этапы измерения и сроки сравнения.
4. F04–F07 и F10–F11 дают материалы, свойства и условия для F17–F19. F15–F16 добавляют сведения об осмотрах и качестве инспекций.
5. F17 + F13–F16 → F18 → F20. F19 + F18/F20 → F21. Точный состав входов каждого вида расчёта определяется отдельно.
6. F22–F23 читают первичные данные и результаты расчётов. Они также должны показывать отсутствие или устаревание результата.
7. F24–F26 сопровождают изменение данных. Историю и права необходимо включать в каждую операцию записи с начала реализации.
8. F29 зависит от паспорта клапана F08 и справочных свойств F07. Для него требуется самостоятельный расчётный контракт.

## Границы переноса

Поля `cardOv`, `compData`, `tmData`, `diagHist`, `eqFlow`, `flowModels`, `dfRes`, `cofRes`, `pofRes`, `riskRes` полезны как источники для миграции. Их структуру нужно сопоставить с предметными сущностями и операциями сохранения.

Пагинация и выборки backend должны поддерживать существующие фильтры, сортировку, выделение и копирование диапазонов. Виртуализация описывает объём DOM и сама по себе не обеспечивает доступ к строкам, которые ещё не загружены с сервера.

Для нового ЕО пустые паспорт, измерение и результат расчёта сохраняют смысл отсутствия данных. Генераторы и демонстрационные подстановки требуют явного режима при переносе тестового набора.

Локальные отметки «проверено» и «режим правки» предстоит связать с полномочиями, автором изменения и защитой от конкурирующей записи. Их текущая реализация описывает интерфейсный сценарий.
