# ADR-001 — Модульный монолит и типизированные предметные данные

Для чтения карточек введена ComponentCardProjection: SQL VIEW собирает DTO из типизированных таблиц конструкций, геометрии и портов. Это разделение командной модели и модели чтения без событийного хранилища: JSON существует только в SELECT-проекции, не как изменяемый мешок фактов. Сервер читает все блоки одной пакетной выборкой вместо 12; запись/аудит продолжают использовать исходные модели под блокировкой версии агрегата. Сериализация без заранее загруженных данных отклоняется, чтобы не скрывать N+1. Числа/false/null/порядок портов и совпадение DTO проверяются через API.

Специальные параметры компонентов обрабатывает ComponentSpecifications по явной ComponentDetailSchema; каждое семейство хранится в собственной типизированной модели. Свободный конец/резьба/КИП — ComponentEndConnection, бобышка — ComponentBossGeometry, арматура — ComponentValveDetails. Материал и исполнение бобышки, PN арматуры не дублируются: используются общие поля компонента/конструкции. Применимость полей отдаётся клиенту метаданными, не определяется по имени. Связанные блоки читаются пакетно только в карточке/команде структуры; расчётные запросы не загружают их автоматически.

Конструкция компонента выделена в ComponentConstruction (11 типизированных полей, HasOne). Пустое чтение/пустой ввод не создаёт строк; отсутствие, false и ноль различаются. Точные типы — справочник ComponentType: FK, разрешённый укрупнённый вид корня и возможность использования элементом. Неизвестная классификация остаётся null; имя компонента не используется для автоматического угадывания типа. Выбор и конструкции сохраняются под общей версией/транзакцией ЕО, а SQL повторяет ограничения положения типа. Внеплановый УЗТ — самостоятельный этап измерений без связи с диагностикой; связь существующего этапа неизменяема. JSON в этих фактах не хранится.

Решение от 09.11.2026. Разработка и приёмка локальные; публикация и перенос на публичный сервер выполняются отдельно.

Приложение остаётся Laravel-монолитом с модулями Equipment, Diagnostics, Installations, ProcessFlows, Catalogs, RBI и Identity/Tenancy. Каждый модуль владеет своими моделями и командами. HTTP-слой проверяет контракт и права, прикладная команда задаёт границу транзакции и блокировку версии агрегата, предметные сервисы выполняют вычисления, слой хранения записывает связанные сущности. Отдельные процессы или универсальные репозитории для каждой таблицы не вводятся.

Паспорт оборудования содержит известные типизированные атрибуты. Они переходят из общего JSONB в столбцы агрегата и связанные блоки классификации, параметров, конструкции, покрытий, среды, коррозионных настроек и диагностических интервалов. Это не EAV: давления и температуры имеют собственные числовые столбцы, даты — date, связи — внешние ключи. Проверка, точность и состояния полей хранятся отдельными строками аннотаций с FK на объявленные поля. API сохраняет объект passport как DTO; SQL-проекция собирает его из таблиц для пакетного чтения без N+1.

JSON уместен в неизменяемом снимке входов/выходов расчёта и событии аудита: там требуется воспроизвести документ конкретной версии. Составы, периоды назначений, ссылки оборудования и измерения должны иметь собственные строки, ключи, ограничения и модели. Остальные JSON-поля проверяются по этому критерию, а не заменяются механически.

Свойства потока (12 объявленных полей) хранятся в process_flow_properties. Отдельные аннотации фиксируют наличие ключа, происхождение и проверку, поэтому неизвестное отсутствующее значение отличается от явно очищенного null, а ноль сохраняется. process_flow_cards — только SELECT-проекция прежнего DTO, пакетно загружаемая связью модели. Принятый расчёт — accepted_calculation_id с составным FK владельца; свойства принятого снимка читаются из неизменяемого process_flow_calculations. UPDATE/DELETE снимков блокируется в PostgreSQL. Миграция сравнивает данные до удаления JSON и проверяется на заполненной карточке с обратным переносом, часовым поясом и микросекундами.

Анкета управления RBI хранит определения разделов/вопросов/пунктов отдельно от типизированных ответов и выбранных пунктов. Модуль Rbi не обращается к прикладным сервисам Catalogs для чтения журнала: общая пагинация/имена участников вынесены в Shared.Application.AuditEvents, а смысловое сравнение ответов остаётся чистым ManagementHistory внутри Rbi.

Параметры среды потока разделены на 28 типизированных колонок process_flow_environments и канонический pH из process_flow_properties. Комментарии и переопределения числовых условий — отдельные строки с FK; размер диапазона связан с определением вопроса, булевым вопросам нельзя записать числовой порог. Нулевые и неизвестные значения не смешиваются. Историческое расхождение двух полей pH не разрешается автоматически: транзакция переноса останавливается до явного выбора значения.

Параметры трубного пространства и самостоятельных змеевиков — equipment_operating_scopes с 21 фиксированным столбцом и отдельными аннотациями. Это дочерние сущности агрегата ЕО: общая транзакция, версия и история, без самостоятельной конкурирующей версии. Трубное пространство разрешено у теплообменника; змеевик ссылается на собственный корневой компонент через составной FK. Владелец области неизменяем. У чтения пустой области есть детерминированный DTO-ID, но запись в БД создаётся только после содержательного ввода. Демонтаж сохраняет параметры, повторное чтение не подставляет значения сосуда. Документированные legacy_keys покрывают пути ТП/ЗМ для дальнейшего явного импорта.

ComponentCode — чистое правило устойчивой нумерации. При создании API допускает исходный code; обычный UI оставляет автоматическую выдачу, а при последующих правках код неизменяем и в PostgreSQL. Числовые корни K-NN и буквенные пространства АВО K-SN/K-CN сохраняются независимо; дочерний код принадлежит своему родителю, счётчик продвигается за наибольший принятый номер. Все 58 исходных кодов 2627 компонентов old проходят проверку. Числовые CML сохраняют соответствие кодам; для АВО старый old иногда выдавал CML по позиции компонента вместо буквенного ID — это отдельное расхождение источника, требующее явной карты владельцев при импорте, а не переименования живых измерений.

Миграция паспорта проверяет полноту ключей, переносит существующие данные и сравнивает проекцию с исходником до удаления JSONB. При ошибке вся миграция откатывается. Перед применением к локальному rline сохраняется дамп. Смена хранения не должна менять расчётные результаты, права, версионирование или форму API.

Дальнейшая работа: завершение миграции и контрактных проверок; перенос классов в модули с сохранением поведения; аудит хранения потоков/справочников; расчётные модули и контрольные наборы old; идемпотентное заполнение локального rline с отчётом расхождений.

### Общий путь записи и встроенные сборки (09.11.2026)

HTTP EquipmentRequest делегирует EquipmentInputValidation, а контроллер — EquipmentCommands. Подготовка импорта использует те же нормализацию, правила и прикладные команды: ограничения применимости, версии, транзакции и аудит не дублируются в загрузчике. Роли и выбор tenant остаются на границе входа. Семантическое сравнение значений вынесено в Shared/Domain/ValueEquality; CatalogValues оставлен совместимым для выпущенных миграций.

Встроенный компенсатор — логическая сборка (ComponentAssembly), а не дополнительный физический компонент. Участники ссылаются на существующие детали того же поддерева; порядок и предшественник хранятся явно. Это сохраняет исходные координаты CML и не удваивает элементы в расчётах ресурса/DF. Номинальное давление, вид, рубашка и НТД сборки — типизированные поля; пустые сборки не создаются автоматически. SQL-проекция возвращает DTO, источником остаются отдельные таблицы.

### План CML и факт замера (09.11.2026)

point_count — плановое число точек, null означает неизвестную схему. Наличие трёх сохранённых координат не доказывает, что план состоял ровно из трёх точек. Измеренные точки хранятся отдельно и сохраняются при неизвестном плане. Его можно один раз уточнить до количества, включающего все сохранённые координаты; изменение уже известной измеренной схемы требует нового CML. SQL проверяет диапазон координат и не допускает их потери. При неизвестном плане агрегат элемента всегда помечен неполным.

Массовая запись этапа проверяется до изменения данных, затем значения/точки upsert пакетами (500 CML / 1000 точек). Неизменённые строки пропускаются. Замер SQL на 24 CML по 3 точки: 48 → 2 INSERT/UPSERT в две таблицы замеров; один дополнительный пакетный SELECT разрешает ID строк. Это не сравнение времени полного HTTP-запроса.

### Паспорт установки и команды дерева (09.11.2026)

FacilityCommands владеет созданием/изменением дерева и установок, FacilityInputValidation — единым контрактом для HTTP и будущего загрузчика. Контроллеры разрешают доступ и сериализуют результат под транзакцией. Версия/аудит — через TenantWrites. Прикладной слой не вызывает HTTP-контроллеры.

Изменяемый passport JSON установок удалён миграцией 000046. InstallationPassport — необязательная HasOne-модель: 17 фиксированных полей с человекочитаемыми столбцами, численными/справочными ограничениями и FK. Repository сохраняет семантику полной замены паспорта; отсутствие поля в запросе сохраняет текущий паспорт, пустой паспорт удаляет необязательную строку. Установка загружает паспорт пакетно; публичные короткие ключи остаются адаптером совместимости. Неизменяемые схемы миграций версионируются (installation-passport-v1.json), экспорт не переписывает выпущенную v1 при изменении описания.
