# Оборудование и паспорт

Первый серверный контур F07/F08. Tenant-БД содержит таблицу `equipment`: UUID, ссылка на установку того же тенанта, код профиля, паспорт JSONB, отметки проверки, состояние active/archived и версия. Реестр читает тот же паспорт. Демо-значения при создании и чтении не подставляются.

## API

- `GET /api/equipment/catalog` — 19 существующих профилей и метаданные 37 базовых паспортных атрибутов: устойчивый ключ, подпись, секция, тип, варианты и применимость.
- `GET /api/equipment` — поиск по имени/позиции/номерам/установке, фильтр группы и active/archived, сортировка по разрешённым полям, пагинация до 100 строк.
- `POST /api/equipment` — создание с установкой, профилем и паспортом. Обязательное паспортное поле — наименование. Остальные отсутствуют, пока не введены.
- `GET /api/equipment/{uuid}` — паспорт с установкой и отметками `{by, at}`.
- `PATCH /api/equipment/{uuid}` — полная замена паспорта, перемещение, архив/восстановление и карта `verification`. Обязательна текущая `version`; устаревшая версия возвращает 409. Профиль через этот метод не меняется.
- `GET /api/equipment/{uuid}/events` — постраничный журнал действий с автором и временем.

Owner/admin создают и изменяют, member читает. Все маршруты требуют доступную tenant-БД и политику входа организации. Нет физического удаления ЕО. Техническая позиция уникальна в установке, включая архив. Сохранение и запись события происходят в одной транзакции с блокировкой версии.

Числовые строки с запятой нормализуются в числа; отрицательные давления отвергаются. Регистрационный номер сохраняется без приписки РТН/ОТН. Год ввода `2020` становится `2020-01-01` с `commissioned_precision=year`. Изменение/очистка проверенного поля снимает проверку; пустое поле проверить нельзя.

## Frontend и проверка

`src/features/equipment` содержит типизированный клиент, адаптер паспорта, выбор установки и реестр на существующем RegistryTable/EquipmentCard/PassportTab. Поиск отменяет устаревшие запросы. Архивирование и перемещение сохраняются вместе с черновиком. 409 оставляет форму; черновик можно скачать до загрузки серверной версии. Переход и закрытие требуют сохранить/остаться/отменить. Выделение и копирование работают по данным страницы, включая виртуально скрытые строки; Ctrl+A означает текущую серверную страницу.

Проверки: `EquipmentTest` на реальном изолированном PostgreSQL; Storybook `R-Line/API/Оборудование` (реестр, пусто, загрузка, ошибка, конфликт, member); `npm run test:equipment:browser` проверяет виртуализацию, sticky, копирование, открытие, сохранение и права. Необходимая миграция существующего тенанта: `php artisan tenant:migrate --tenant=rline`.

## Оставшийся объём

Это базовый контур, а не завершение F07/F08. Полное сопоставление профильных паспортов, полный ФТС, перенос browser cardOv, согласованная смена профиля, дополнительные виды фильтров/представлений/экспортов остаются в плане. Доступны базовый паспорт, состав, диагностики, УЗТ, коррозия/ресурс и история. Остальные вкладки ещё подключаются.

## Состав, диагностики и УЗТ

Отдельные tenant-таблицы: `equipment_components`, `equipment_inspections`, `equipment_cmls`, `equipment_thickness_stages`, `equipment_thickness_values`. UUID связей независимы от порядка. K-NN, K-NN.SN и CML-NN[.N].N назначаются сервером монотонно. Демонтаж не удаляет историю; изменение порядка и восстановление сохраняют коды. Тип/родитель/принадлежность CML не меняются. Змеевик — самостоятельный корневой компонент с собственной областью расчёта.

PATCH паспорта принимает необязательные `structure`, `inspections`, `thickness`. Это изменения дочерних записей в общей транзакции с версией ЕО; отсутствующие записи сохраняются. React отправляет только изменённые дочерние записи и замеры. При конфликте не применяется ни одна часть карточки. Физическое удаление компонентов с замерами отсутствует.

Первичное ТО сосуда создаётся всегда: РТН → ТО-2, ОТН → ТО-1. Пустые даты остаются пустыми. Этапы УЗТ создаются для первичного ТО и выполненных ТО-1/ТО-2/ЭПБ/внепланового УЗТ; ГИ/ПИ/ГЕОД-И/НО колонок УЗТ не создают. Фактическая дата толщинометрии отделена от даты диагностики. `null` в точке — не замерялась, `0` — нулевой замер. Автогенерации толщин нет. Проверенный этап блокирует дату и точки; снять проверку нужно отдельным сохранением. Проверка хранит автора и время. Изменение количества точек CML с сохранёнными замерами запрещено.

Клиент использует прежние ComponentList, DiagnosticsTab, ThicknessTab и CorrosionResourceTab. Оболочка EquipmentCard общая. У генерации UUID есть fallback через криптографический getRandomValues для локальных HTTP-хостов.

## Коррозия и ресурс — текущая реализация

Чистое ядро `CorrosionCalculator`: MIN/AVE/MAX по заполненным точкам элемента; метка неполноты; долгосрочная скорость от Sном с 01.01 года ввода и от первого замера; краткосрочная от предыдущего имеющегося замера. Отрицательные скорости сохраняются. Приоритет отбраковки ЭПБ → паспорт, наследование свойств элемента от компонента. Ресурс округляется вниз до 0,1; V≤0 → infinite, Sфакт≤Sотбр → 0. Износ ограничен 0–100%. Сводки сосуда и каждого змеевика раздельны. Предупреждение ресурса сравнивается с ближайшей невыполненной плановой записью ТО-1/ТО-2/ЭПБ/УЗТ.

`NormativePeriodicity` реализует переданные проектные правила ФНП/ИТНЭ/РУА, максимальную скорость только сосуда, проектную скорость и историю периодичности по датам УЗТ. Действующие периодичности хранятся отдельно; применение требует режима правки и не переносит плановые даты. GET карточки разрешает все части ответа внутри read-only REPEATABLE READ транзакции. Схемы вложенных ответов и infinite генерируются Scramble.

Расчётные ряды CML используют то же ядро, что элементы; сводки считаются по элементам. Реализованы все переданные проверки аномалий: copypast/сдвиг, настройка прибора, вероятная замена, резкое утонение, отклонение точки от медианы и дата замера. Сигналы не изменяют точки: они показываются в УЗТ, коррозии/ресурсе и списке ФТС.

Остаток этого блока: точное расположение парных колонок элемент/CML и объединённых ячеек УЗТ, графики трендов и полный XLSX/PDF, расчёт дат от действующей периодичности с поглощениями, соединения и специальные атрибуты трубных пучков. Есть выгрузка сохранённой карточки и страницы реестра в UTF-8 CSV; это не XLSX. Эти пункты не считаются реализованными наличием базовой вкладки.

## Графики диагностики и переходы

`GET /api/diagnostic-schedule` читает ЕО и компактную SQL-сводку по видам: MAX выполненной даты и MIN плановой даты невыполненных записей. Полные истории и расчёты карточек в список не загружаются. Пагинация применяется до агрегации; ответ содержит `as_of` — серверную дату для оценки просрочки. Весь ответ разрешается в read-only REPEATABLE READ транзакции.

Поддержаны поиск/группа/установка/архив, состояния all/overdue/upcoming/missing, горизонт within_days и сортировка next_on с пустыми значениями в конце. ГИ/ПИ может использоваться как объединённый вид. Плановые даты пока вводятся отдельными невыполненными записями; авторасчёт дат с поглощениями остаётся в плане.

React сохраняет существующую DiagnosticSchedulePage и виртуализацию, закреплённую позицию, выделение мышью/Shift/Ctrl+A и копирование невидимых строк страницы. Общий API-поиск ищет действующие/архивные ЕО и открывает UUID через единый navigation guard. Его контракт явный: handled — форма перехватила переход, continue — выполнить один раз. Подтверждения оборудования и установок выводятся portal-слоем поверх поиска. Escape обрабатывает верхний слой; закрытие не теряет черновик.

Проверки: `npm run test:equipment`, `npm run test:equipment:browser`, `npm run test:diagnostics:browser`. Реальные переходы через поиск, несохранённый паспорт установки, графики, замеры и конфликт двух сеансов проверены на локальном testing; временные данные удалены. Основная строка состояния подключённых страниц обозначает серверный источник, браузерный snapshot не выдаётся за серверный экспорт.
