# Установки и структура предприятия

Базовый серверный сценарий реализован 07.11.2026. Страница «Технологические установки» в авторизованном приложении читает API; обычные демонстрационные stories прежней страницы продолжают использовать локальную модель. Новые истории API находятся в Storybook → R-Line → API → Установки.

## Сценарий пользователя

1. Откройте «Технологические установки» → «Структура предприятия».
2. Создайте предприятие, затем площадку с этим родителем, затем производство в площадке. Кнопка с названием существующего узла открывает его правку.
3. Закройте структуру и нажмите «+ добавить». Укажите имя установки и производство.
4. Откройте паспорт, нажмите «✎ edit», заполните данные и сохраните. Размещение также можно изменить в режиме правки.
5. Откройте установку во втором сеансе: он читает тот же сохранённый паспорт из PostgreSQL.

Owner/admin могут создавать и менять данные своего тенанта. Member имеет доступ на чтение; признак администратора платформы сам по себе не заменяет предметную роль в организации. Все запросы защищены существующими cookie/CSRF/MFA/членством и ограничениями стенда.

## Данные и правила

- В каждом tenant-PostgreSQL находятся `facility_nodes`, `installations`, `domain_events` и своя таблица `migrations`. В общей БД эти предметные таблицы не создаются.
- Структура фиксирована: enterprise → site → production → installation. Корневое предприятие без родителя; остальные уровни требуют непосредственного родителя нужного типа. Тип узла после создания неизменяем, поэтому перенос не создаёт циклы. Чужие UUID не находятся в текущей tenant-БД.
- ID — UUID; имя обязательно, остальные поля паспорта могут быть пустыми. Коды размещений уникальны среди узлов данного тенанта, шифры установок — среди его установок; пустой код допускается.
- Паспорт включает назначение, полное наименование, ввод в эксплуатацию, мощности и единицу мощности, проектировщика/лицензиара, ОПО/категорию, атмосферу, площадь, персонал и ответственных. Мощность требует указать единицу; численные поля неотрицательные, персонал — целое число. Десятичная запятая принимается и нормализуется в JSON-число.
- PATCH требует `version`. При несовпадении сервер возвращает 409 и не записывает изменение. React сохраняет черновик, а отдельная кнопка явно загружает серверную версию со сбросом черновика. Нет скрытой перезаписи последней версии.
- Запись данных и событие с автором/снимками до и после выполняются в одной tenant-транзакции. Отмена правки не отправляет PATCH. Переход с открытым черновиком требует решения сохранить/выйти/остаться.
- Списки и выбор размещения читаются постранично (30 по умолчанию, максимум 100); поиск — имя/код и имена предков размещения. При ошибке серверные данные не заменяются локальными демо-значениями.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET/POST | /api/facility-nodes | Список/создание узла |
| PATCH | /api/facility-nodes/{node} | Правка с проверкой версии |
| GET/POST | /api/installations | Список/создание установки |
| GET/PATCH | /api/installations/{installation} | Паспорт/правка с версией |
| GET | /api/installations/{installation}/events | Постраничный журнал действий |

Ответы ресурсов содержат `data`; пагинация списков — `data`, `links`, `meta`. Журнал пока использует стандартную пагинацию Laravel. Форматы, ограничения и примеры заголовков опубликованы в Scramble. Генератор получает метаданные tenant-моделей через `TenantModelTypes`, без открытия БД конкретной организации. `FacilitySchemaTransformer` дополняет сериализованный объект паспорта из правил FormRequest и исключает запрещённые поля создания.

## Миграции

```sh
docker compose exec app php artisan tenant:migrate
docker compose exec app php artisan tenant:migrate --tenant=rline
```

Команда обновляет подготовленные tenant-БД, не переносит демо-данные и возвращает ненулевой код при ошибке. Миграции идемпотентны, защищены advisory lock, перед запуском проверяется tenant_identity. Новая организация получает эту же схему при provision; ready публикуется после успешных миграций. Предметные миграции лежат отдельно в `database/tenant-migrations`; обычная центральная migrate их не применяет.

На текущем локальном стенде миграция rline применена. При обновлении backend необходимо также перезапускать worker (`php artisan queue:restart`).

## Проверка

Проверены реальные PostgreSQL-БД двух тенантов, чужие ID/родители, роли, отрицательные значения, единицы, поиск, аудит, конфликт версий и повтор миграций. В браузере на testing выполнены вход с TOTP, создание дерева/установки, сохранение паспорта, чтение во втором независимом сеансе с резервным кодом, конкурирующая правка и защита навигации. Временная проверочная учётная запись и созданные ею данные удалены.
